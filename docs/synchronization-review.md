# 全局同步机制复查

范围：`app/src/main` 全部生产源码、关联测试、构建配置。继续在 PR #28 修改；不改变页面布局、协议字节、温度校准或用户操作方式，不在本地运行编译/Gradle。

原则：先明确状态归属、事件和生命周期，再决定同步机制。协程 Mutex 仍属于锁；把锁改名为 Channel 令牌、把延时换成别的计时 API，都不算解决问题。

## 替代方案与约束

| 位置 | 原问题 | 处理与保持的约束 |
|---|---|---|
| `ble/ModeCommandCoordinator.kt` | 用业务 Mutex 跨挂起点串行模式切换 | `CommandMailbox` 单消费者处理完整 OFF/ON 与安全关闭命令；新意图立即使旧意图失效，不等队列；安全关闭不创建用户意图。断开立即失效并关闭旧会话邮箱 |
| `ui/CoolerViewModel.kt`、`ProfileMutationCoordinator.kt` | 删除档案和连接记录靠 Mutex 协调；删除对象来自可能落后的 UI 缓存 | 业务事件单消费者拥有忽略的会话集合。删除事务返回实际删除对象，开始及提交后均核对当前连接快照，成功后屏蔽涉及的匹配会话；挂起期间同地址重连也不会被排队记录立即重建。 |
| `ble/BleManagerHolder.kt` | `get` 使用双重检查锁，owners 却按主线程访问，契约不一致 | 所有入口统一 MainThread 契约及运行时检查，删除 synchronized/volatile；Tile 的 lazy 也使用无锁主线程方式 |
| 连接发现 | 成功连接后额外等300ms，没有明确型号/日志证据支持普遍等待 | 在已校验会话身份的连接回调上立即发现；保留真正的发现超时、防重及迟到回调隔离 |
| `ble/GattOperationQueue.kt` | 每次操作完成后再等60ms；注释将无证据的间隔称为固件要求 | 成功/过期操作根据实际回调释放 lane，无固定成功间隔；超时 lane 仍只能由排空回调或会话销毁恢复 |
| 遥测等待 | 控制忙、没有可用目标、隔离中也周期性执行空遍历 | 由控制完成、通道可用性和真实采样/恢复截止时间驱动；没有工作时挂起，时间经过不等于旧回调已排空 |
| 温度恢复 | 用 `now - 4000` 修改“最近报告时间”来安排下次恢复 | 分离真实温度报告时间与恢复尝试时间，不伪造数据新鲜度 |
| `data/ProfileRepository.kt` | 坏 JSON 使观察流终止，被当成瞬时 I/O 每2秒反复解析 | 解码错误按快照报告，保持 DataStore 订阅；下一份合法快照或清引用事件直接恢复，不产生假的空列表/null |
| 存储恢复 | retry 总次数决定是否提示，成功恢复后的第二次故障不再报告 | 每个收集者记录故障期，成功数据重置；真正上游 I/O 才进行退避重订阅 |
| 服务通知 | 语言读失败重启整个 combine，期间 BLE 状态不能刷新通知 | 语言分支单独恢复；初始系统语言只提供一次，之后保持最后语言，BLE 状态持续驱动通知 |
| `domain/CoolerDevice.kt` | 无生产读取的扫描时间戳参与 equality，使相同广播被当成新状态 | 移除时间戳；真正广播值变化仍更新 UI，相同数据由 StateFlow 去重 |

`util/CommandMailbox.kt` 是真正的工作队列而非互斥许可：生产者提交动作及独立回复，只有一个生命周期拥有的消费者执行动作。等待者取消可丢弃尚未开始的动作，但不能打断已开始的事务/设备操作；关闭后排空已接收动作，scope 结束清理回复。禁止在消费者动作内部递归等待同一邮箱。

## 保留的机制与理由

- **底层 GATT lane 的一个协程 Mutex**：Android 一次只允许一个回调型操作在途，回调没有应用请求序号。即使调用者取消，也不能让已经接受的操作提前让出 lane；由实际回调、明确超时隔离或 teardown 结束。锁仅约束物理传输，不负责 UI 状态、用户意图或业务事务。`CompletableDeferred` 承接平台完成事件，`NonCancellable` 防止取消错误释放 lane。
- **GATT/连接/发现超时**：平台可能永远不回调，必须有失败上界。超时不被视为成功，也不无条件允许重用旧 lane。
- **120ms、最多一次的 GATT 失败重试退避**：仅在平台明确拒绝或失败回调后缓解瞬时忙/失败；不是成功同步屏障。已接受却没有回调的请求不重试。
- **遥测正常500ms采样、连续失败后4s退避；RSSI 2s采样**：一些设备/字段没有可靠推送，RSSI 本身是主动测量。没有依据仅因 Notify 属性而删除读取；不改变原有采样功能。通道明确不可用时不执行空采样。
- **未知 RGB 最短4s回读、默认灯恢复3s限流且每会话至多3次**：限制对设备的主动恢复流量，不用来判定操作完成；仍服从通道隔离和会话有效性。
- **风扇150ms、RGB 200ms输入防抖**：合并连续用户输入，减少无线写入；不是等待回读同步。发送前仍检查最新命令身份。
- **真正 DataStore I/O 失败后的2s重订阅退避**：底层存储没有通用的“磁盘已恢复”事件，需保留无人值守恢复能力；只对 IOException 生效、可以取消、保持最后有效值，不吞编程异常。坏 JSON 的逐快照错误不走此计时路径。
- **BootReceiver 8s预算**：为 `goAsync` 异步工作设上界并在 finally 中 finish；它是应用预算，不是假定平台精确截止时间。
- **Handler.post**：仅将平台/Binder 回调投递到 Main，避免 connectGatt 返回前的同步回调重入；没有 postDelayed，也不以毫秒判断就绪。
- **Service Channel、StateFlow、DataStore.edit、生命周期 Job**：分别拥有命令顺序、状态快照、原子持久化和资源退出，属于应保留的框架机制。测试 DataStore 的 Mutex 用来模拟框架原子事务，不是生产业务锁。
- **档案元数据时间和会话 ID 的单调时钟种子**：生成身份/记录时间，不进行等待、轮询或状态同步。动画时间同样不属于业务同步补丁。

## 验证

测试用 `CompletableDeferred` 与协程调度器控制事件顺序；只对真实采样/重试/超时语义推进虚拟时间，不依赖 sleep 或机器执行速度。

覆盖邮箱顺序、取消和生命周期；模式替代/安全关闭/断开；删除与记录交错；GATT 立即完成和超时排空；遥测空闲/控制忙/隔离/通知恢复；坏快照修复及通知语言故障隔离。实际通过数量、Lint 和 APK 结果以 PR 最新 GitHub Actions 为准。

未进行 BLE 实机或视觉回归。移除300ms/60ms固定等待并不等于证明所有固件均无兼容性要求；如实机发现问题，应记录具体型号、状态/回调日志和失败路径，验证设备特定策略，不能恢复无依据的全局延时。建议实机检查连接成功率、快速模式切换、每分钟 GATT 操作量、通知缺报恢复及断线重连。
